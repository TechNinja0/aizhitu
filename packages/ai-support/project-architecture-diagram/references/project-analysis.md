# 项目分析与证据

## 从入口收敛范围

先读取项目的 Agent 约定、README、已有架构文档和目录清单。优先 `rg --files`，排除依赖缓存、构建产物、第三方 vendor 和生成代码；不要一次读完整仓库。只读取任务相关内容，不采集密钥、生产数据或无关用户文件。

按项目技术栈选择构建线索，例如 `package.json`/workspace 配置、Gradle settings 与模块依赖、Maven modules、Go modules、Cargo workspace、Xcode target 或 Swift Package、HarmonyOS 模块配置。构建依赖只能证明静态依赖，不能直接当作网络请求或数据流。

再沿入口查具体实现，例如应用启动、路由注册、依赖注入、网络客户端、事件发布与订阅、数据库访问、任务调度。部署图读取实际部署配置；只有仓库文件时说明“配置视角，未验证线上部署”。不要为了确认架构启动业务服务、安装依赖或连接生产环境。

## 选择一种关系语义

| 视角 | 节点与边 | 证据 |
| --- | --- | --- |
| 模块架构（默认） | 业务模块、公共层；调用或依赖 | 模块清单、入口、接口与调用实现 |
| 系统上下文 | 当前系统、使用者、外部系统；交互 | 接口定义、客户端、集成配置 |
| 请求或数据流 | 入口、处理、存储；数据方向 | 调用点、处理器、读写或消息实现 |
| 部署 | 进程、容器、服务、存储；通信 | Docker/编排/基础设施配置 |
| 目标方案 | 计划组件与关系 | 用户要求、PRD、设计文档，明确标注规划 |

箭头从调用方指向被调用方，静态依赖从依赖方指向被依赖方，数据流按实际传递方向。标签写明“调用”“依赖”“发布”“读取”等；混用关系时必须有图例。不要将目录包含、代码依赖、网络访问画成没有语义区别的箭头。

## 同名 Markdown 的最小内容

```markdown
# <项目／模块>架构说明

范围与视角：当前实现的模块架构；覆盖……，未覆盖……。
分析基线：分支／commit（可用时），相关工作区未提交变化，读取日期。

| 图中 ID | 组件或关系 | 证据位置 | 类型 | 说明 |
| --- | --- | --- | --- | --- |
| api | API 模块 | src/server.ts:实际行号，bootstrap 符号 | 代码事实 | 入口注册 |
| api-store | API → 存储 | src/repository.ts:实际行号，save 符号 | 代码事实 | 调用持久化接口 |

图例：实线为已核实关系；虚线且标注“待核对”为尚未核实关系。
待核对／冲突：列出对象 ID、问题、待确认来源；没有则写无。
检查：实际命令、结果和未执行项；预览是否实际查看。
```

上表仅示范格式，实际文件路径、行号、符号和节点必须来自当前输入。关系也需要证据，不能只有节点说明。一个组件可由多个文件共同支持；无需列出每个类或每条 import。文档与代码冲突时，当前实现图依代码绘制并记录冲突，目标方案图按方案绘制并标明实现差距。
